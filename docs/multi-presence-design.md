# 멀티 참가자 접속 상태(presence) — 창을 통째로 닫아도 방에서 나가게 (O-018 설계, 2026-09-22 진행 예정)

> 상태: **구현 완료(2026-09-22)** — §6 권장안 5건 확정 후 레드팀에서 **2·3·4번을 교체**했다. 최종 결정·근거·검증은 `docs/verification/records/2026-09-22_multi-presence.md` §3 이 기준이다. 아래 §6 은 09-21 초안 그대로 두고 §8 에 바뀐 점만 적는다.
> 배경 기록: `docs/verification/records/2026-09-21_multi-unload-token.md` §8 6a, open-issues O-018·O-019.

## 1. 문제
지금 방에서 나가는 경로는 셋이다: 명시적 `/leave`·`/leave-to-lobby`, 그리고 **브라우저가 보내 주는 나가기 신호**(`pagehide` → `sendBeacon /unload`, 2026-09-21 부터 페이지 토큰). 셋 다 **클라이언트가 무언가를 보내야** 한다. 보내지 못하면 서버는 모른다.

| 상황 | 신호 | 결과 (현재) |
|---|---|---|
| 탭 하나 닫기·방 밖으로 이동 | 옴 | 8초 뒤 나감 ✅ (운영 확인 09-21) |
| **시크릿 창 전체 닫기** | **안 옴** (운영 nginx 로그에 `unload` 없음, 09-21) | 유령 참가자 |
| 브라우저 강제 종료·PC 절전·크래시 | 안 옴 | 유령 |
| 모바일: 앱 전환 뒤 OS 가 탭을 버림, 네트워크 끊김 | 대개 안 옴 | 유령 |
| WebSocket 이 안 돼 폴링으로 도는 사용자 | 탭 닫기는 옴 / 위 경우는 안 옴 | 유령 |

유령의 비용: 대기실에서 **최대 24시간**(`RoomCleanupBatch` WAITING 기준) 자리를 차지하고, **유령이 방장이면 아무도 게임을 시작하지 못한다**. 게임 중 방장이 유령이면 라운드 진행(방장 전용)이 멈춘다 — PLAYING 방은 2시간 뒤 배치가 끝낸다.

## 2. 방향 — 서버가 "연결이 살아 있는지"를 직접 판단
멀티 화면(대기실·플레이·결과 비방장)은 이미 방 토픽(`/topic/room/{code}`)을 **WebSocket 으로 구독**한다. 창을 닫든 브라우저가 죽든 **TCP 연결은 끊기고**, 끊김은 서버가 스스로 안다(Spring `SessionDisconnectEvent`). 이것을 나가기 판단의 두 번째 근거로 쓴다.

```
구독(SUBSCRIBE /topic/room/X)  → 그 (방, 회원)의 활성 연결 집합에 sessionId 추가 + 예약된 나가기 취소
연결 끊김(DISCONNECT·UNSUBSCRIBE) → 집합에서 제거 → 집합이 비면 유예(G초) 뒤 나가기 예약
유예 중 같은 (방, 회원)이 다시 구독 → 취소 (새로고침·페이지 이동·일시적 재연결)
```

**순서 문제(09-21 결함)가 구조적으로 안 생기는 이유**: 판단 기준이 "요청이 도착한 순서"가 아니라 **연결 집합이 비었는가**다. 새 페이지의 구독이 옛 연결 종료보다 먼저 도착해도 집합은 {옛, 새} → {새} 로 비지 않는다. 늦게 도착해도 {옛} → {} (예약) → {새} (취소) 다.

기존 경로는 그대로 둔다: 탭 닫기 신호(페이지 토큰)는 **빠른 경로**(8초), 연결 끊김은 **안전망**(G초). 둘 다 같은 `RoomUnloadService` 대기 목록을 쓰므로 페이지 GET·재참가·구독 중 무엇이든 취소한다.

## 3. 구성 요소
| # | 무엇 | 어디 | 비고 |
|---|---|---|---|
| 1 | 활성 연결 집합 `Map<"방:회원", Set<sessionId>>` + 역방향 `Map<sessionId, "방:회원">` | 새 `RoomPresenceService` (또는 `RoomUnloadService` 확장) | 인메모리(단일 인스턴스 — 기존 토큰·대기 목록과 같은 전제) |
| 2 | 구독 등록 | `WebSocketAuthInterceptor` 가 SUBSCRIBE 를 **허용한 직후** 또는 `SessionSubscribeEvent` 리스너 | 인가를 통과한 구독만 센다. sessionId 는 `accessor.getSessionId()` |
| 3 | 끊김 처리 | `@EventListener SessionDisconnectEvent` / `SessionUnsubscribeEvent` | disconnect 이벤트에는 destination 이 없어서 역방향 맵이 필요 |
| 4 | 유예 뒤 나가기 | `RoomUnloadService` 에 `scheduleLeaveOnDisconnect(room, member)` — 기존 `applyLeave` 재사용(위임·방 종료·브로드캐스트 동일) | 유예 G 는 탭 닫기(8초)와 별도 설정 `game.multi.disconnect-grace-ms` |
| 5 | **하트비트** | `enableSimpleBroker("/topic").setHeartbeatValue(new long[]{10000, 10000}).setTaskScheduler(...)` | 지금은 하트비트가 **없다**(설정 0건). 창 닫기는 TCP 종료로 즉시 알지만, 네트워크가 조용히 끊긴 경우(모바일·절전)는 하트비트가 있어야 감지된다. stompjs 2.3.3 클라이언트 기본값이 10초/10초 — 협상 결과와 서버의 끊김 판정 시점은 **구현 때 테스트로 확인**(추정 금지) |
| 6 | 결과 화면 방장도 구독 | `multi-result.js` 는 지금 **비방장만** WS 연결 | 방장이 결과 화면에서 구독이 없으면: 플레이 화면 연결 끊김 → 유예 중 방장이 재시작 → 방이 WAITING 으로 바뀐 뒤 나가기 적용 → **방장이 자기 방에서 쫓겨남**. 방장도 구독하게 하거나(권장), 재시작이 예약을 취소하게 한다 — 반드시 테스트 |

| # | 공격 | 대응 |

## 5. 테스트 계획
**자동 (실패 테스트 먼저)** — `SessionLifecycleContractTest` 처럼 `RANDOM_PORT` + `WebSocketStompClient` 로 실제 서버에 붙는다(저장소에 선례 있음).
1. 구독 후 연결을 끊고(소켓 종료) 아무것도 안 함 → G 뒤 `LEFT`, 방장이면 위임 — **오늘의 "창 전체 닫기"**
2. 끊고 G 안에 새 연결로 재구독 → 유지 (새로고침)
3. 새 구독을 먼저 만들고 옛 연결을 나중에 끊음 → 유지 (순서 뒤집힘)
4. 연결 2개(탭 두 개) 중 하나만 끊음 → 유지, 둘 다 → `LEFT`
5. 게임 중 방장 연결 끊김 → G 뒤 위임, 방 `PLAYING` 유지
6. 결과 화면 방장: 플레이 연결 끊김 → G 안에 재시작 → **방장 유지** (§3-6)
7. 인가 실패한 구독은 집합에 안 들어감
8. 하트비트: 클라이언트가 하트비트를 멈추면 서버가 끊김으로 처리하는지(시간은 측정해서 기록)
테스트 프로필은 G 를 짧게(예: 200ms).

**로컬 실브라우저**: 내장 브라우저 `localhost`·`127.0.0.1` 두 세션(로컬 `o001b` 계정 있음). 내장 브라우저는 탭 닫기 신호를 안 보내므로 오히려 "신호 없이 끊김"을 재현하기 좋다 — 탭을 닫고 G 뒤 위임 확인.

**운영 (배포 후, 개발자와 같이)**: ① 시크릿 **창 전체** 닫기 → G 뒤 위임(09-21 실패 항목) ② 새로고침·게임 시작·결과·재시작 회귀(R-025) ③ 휴대폰으로 대기실 → 카톡 30초 → 복귀 시 자리 유지 ④ 배포 중 게임 유지(가능하면).
