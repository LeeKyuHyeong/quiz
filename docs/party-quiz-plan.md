### 1-2. PERSON(인물맞추기) — 로컬 확정으로 사진이 기본

- 운영 서버였다면 사진은 불가(복제·전송)였지만 **로컬 노트북에만 두고 현장에서만 띄우는 것으로 확정**(§10-1: 제30조 사적 복제 여지 + 제29조 현장 공연). 조건은 §3.
- **확정 흐름(패턴 A)**: 보드에 **사진**을 띄운다 → 외침 → MC [팀 정답] → 정답 공개 → [다음 라운드]. 끝. 사진을 띄우는 순간 힌트는 의미가 없으므로 힌트·목소리 없음. 항목 = 사진 1장 + 정답 + 보조 정보(직업·대표작, 정답 공개 때만).
- 사진 변형(선택): 어릴 적 사진, 눈만 보이기, 뒷모습. 항목당 사진은 1장이므로 변형은 별도 항목으로 등록.
- "우리끼리 인물"(고등학교 선생님·동창)은 여자친구 쪽이 전혀 모르니 넣어도 번외 1~2문제만.

### 1-4. 스피드퀴즈 — 본게임 첫 대분류 선택권을 정하는 몸풀기 (본게임 전, `party` 브랜치)

몸으로 말해요와 스피드퀴즈는 앱 입장에서 같은 엔진(제시어·타이머·정답/패스)이고 "말로 설명 / 몸으로만"은 진행 규칙이라 **한 화면으로 둘 다** 한다. 턴 시작 때 설명 방식만 골라 보드에 띄운다.

- 경로 `/admin/party/speed`(콘솔)·`/admin/party/speed/board`(보드), 본게임과 같은 2창·보드 1초 폴링(§4-1). 제시어는 `party_item` category `SPEED`(TEXT, `answer`=제시어, `sub_category`=주제: 동물·영화·직업·물건·동작…).
- **설정(결정 1)**: 주제 선택(전체 가능) + **팀별 제한 시간 초**(남팀·여팀 각각 입력 — 임산부 배려로 다르게 둘 수 있음) + 설명 방식(말로 / 몸으로).
- **한 턴(결정 2)**: 팀 선택 → [시작] → 그 팀의 초로 타이머 → 제시어 표시 → 출제자 1명이 설명, 나머지 6명이 맞힘 → MC [정답] / [패스] → 다음 제시어(출제자 교대) → … → **시간이 끝나면 제시어 표시가 멈추고 정답·패스 버튼이 잠긴다(결정 3)** → 정답 수 확정.
- **제시어 표시 위치**: 기본 **보드(TV)**. 출제자가 TV 를 보고 설명하고 맞히는 6명은 TV 에 등을 돌린다 — 제시어마다 출제자가 바뀌어도 자리만 바꾸면 되므로 교대가 빠르다(노트북 옆에 서서 보는 방식은 교대마다 사람이 움직여야 함). 설정에서 "콘솔에만 표시"로 바꿀 수 있고, 그때 보드엔 제시어가 안 나온다.
- **보드에 보이는 것(결정 4)**: 팀 이름 · 남은 시간 · **정답 수** · 패스 수 · (보드 표시일 때) 현재 제시어 · 설명 방식. 두 팀 다 끝나면 정답 수 나란히 + "첫 선택권: ○팀".
- 출제자 교대: 앱은 이름을 관리하지 않는다. **제시어마다 교대(확정 10-06)**, [정답]/[패스]를 누르면 **제시어가 바로 다음으로 바뀐다** — "다음 출제자!" 같은 안내 화면 없음. 움직이지 않고 맞히기만 하는 예외 인원은 현장 처리. 팀별 제한 시간 입력은 남기되 실제로는 같은 값으로 쓸 예정.
- 승부: 두 팀 **정답 수** 비교(시간이 달라도 정답 수로 — 그게 핸디캡의 의도). 동점이면 MC 재량(30초 재대결 등). 결과는 본게임 점수와 분리, 본게임 첫 대분류 선택권만 걸린다.
- 출제된 제시어는 같은 세션에서 다시 안 나온다. [되돌리기] 1단계(직전 정답·패스 취소). 시간 종료 뒤엔 [되돌리기]만 된다.
- 개발량: 상태 객체 1(`SpeedQuizState`, **서버 전체 1개**(싱글턴 홀더, §4-3): 설정·팀별 결과·출제 ID·현재 턴 시작 시각) + 액션(설정 저장·턴 시작·정답·패스·되돌리기·턴 종료) + 템플릿 2 + JS 2. 타이머는 콘솔 JS 가 세고 0 이 되면 서버에 턴 종료를 보낸다. 서버도 시작 시각을 알고 있어 새로고침 뒤 남은 시간을 복구한다. 본게임 `PartyGameState` 와 분리하고 서로 참조하지 않는다.

### 2-3. 로컬 실행 환경 (노트북) — 노래 데이터는 운영에서 가져와야 한다

- 노트북: JDK 17 + MariaDB 11 + 저장소 클론(또는 WAR). `application-dev.properties` 가 `localhost:3306/song`(root) 를 보므로 노트북 로컬 DB 를 같은 이름·계정으로 만들면 설정 변경 없음. 기동 `./mvnw spring-boot:run -Dspring-boot.run.profiles=dev` → 8082.
- **노래 데이터(질문의 답: 필요하다)**: 운영 DB 에서 `genre`·`song` **두 테이블 데이터만** 덤프해 로컬에 적재한다. 나머지 테이블은 `schema.sql` 로 빈 구조만 만든다(`validate` 통과용). `member` 를 안 가져오므로 회원 개인정보가 노트북에 남지 않고, 회원 0명이면 `DataInitializer` 가 관리자 `a@a.com` 을 만들어 준다(비밀번호는 코드). `song_answer` 는 텍스트 판정을 안 하므로 불필요.
  ```bash
  # 서버 (runbook §4-1 과 같은 컨테이너). 'song genre song' = DB song 의 genre·song 테이블
  docker exec quiz-db sh -c 'mariadb-dump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-create-info song genre song' \
    | gzip > /root/backup/party-songs-$(date +%Y%m%d).sql.gz
  # 노트북
  mariadb -uroot -p -e "CREATE DATABASE song CHARACTER SET utf8mb4"
  mariadb -uroot -p song < src/main/resources/sql/schema.sql            # 빈 구조 (party_item 포함)
  gunzip -c party-songs-YYYYMMDD.sql.gz | mariadb -uroot -p song        # genre → song 순서로 적재
  ```
  덤프는 리허설 1 전에 한 번, 12월 첫 주 동결 때 한 번 더(그 사이 운영에 곡이 추가됐을 수 있음). 두 번째는 `TRUNCATE song; TRUNCATE genre;` 뒤 재적재(FK 순서 주의).
- 행사 전 재검증: 로컬 관리자에서 `YouTubeVideoCheckBatch` 수동 실행 → `is_youtube_valid=0` 곡은 파티 조회에서 제외. 배치 설정은 `BatchService` 가 로컬에서도 seed 한다.
- 이미지 폴더: `WebConfig` 리소스 핸들러가 쓰는 업로드 경로(dev 속성) 아래 `party/`. **저장소 밖 경로**로 잡고 `.gitignore` 에도 넣는다. 등록 폼 업로드는 확장자 화이트리스트(jpg·png·webp) + UUID 파일명.
- **USB 백업**: 로컬 DB 덤프(`party_item` 포함) + 이미지 폴더 + WAR + 기동 배치 파일. 목표는 "노트북이 죽으면 다른 PC 에 30분 안에 복구" → 리허설 2 에서 복구 리허설 1회.
- 코드 관리: 파티 코드는 **`party` 브랜치**에 둔다. `PartyItem` 엔티티가 main 에 올라가 배포되면 운영 DB 에 `party_item` 이 없어 `validate` 가 실패하기 때문. 나중에 운영에 올리고 싶으면 운영 DB CREATE 후 병합.

- **현장 재생**: 저작권법 제29조 제1항(비영리·무대가·무보수 공연) 범위. 참가비 없음 유지. 선물은 MC 가 사는 것이라 청중 대가가 아님.
- **YouTube 정책**(2026-09-29 원문): 오디오·비디오 분리 금지(Developer Policies III.I.7), 플레이어 기능 차단 금지(III.I.6), 최소 200×200·오버레이 금지·보일 때만 자동 재생(Required Minimum Functionality). 파티 모드는 AUDIO 도 콘솔에 480×270 으로 보이게 재생, VIDEO 는 보드에 크게. 현재 사이트의 `0×0` 숨김은 O-025.
- **장면 맞추기**: 운영 서버였다면 캡처 불가(인용 요건 미충족, 서버 저장은 복제·전송)였으나 **로컬 확정으로 캡처 1장 사용**(§10). 정답 공개에 작품명·방송사(출처)를 표시. 공식 클립 임베드(VIDEO)는 대안으로 남겨 둔다.

## 4. 화면·동작

### 4-1. 두 창
- **콘솔(노트북)** `/admin/party/console`: 라운드 번호·팀 점수, 대분류·중분류 선택(남은 문제 수 표시), 문제 카드(**정답 + 인정 답안 + 보조 + 출처 + 대분류 판정 규칙 한 줄** — MC 만, 문제를 띄우기 전에 보임. 노래는 `SongAnswer` 변형을 인정 답안 자리에), AUDIO 플레이어 480×270, 재생/정지/처음부터, 타이머, **[남팀 정답] [여팀 정답] [못 맞힘]**, 재생형에서 **[남팀 오답] [여팀 오답]**(점수 무관, 보드 표시용), GAME 에서만 [힌트 열기], 점수 ±, 다음 라운드, 이력, 종료(결과 JSON).
- **보드(TV)** `/admin/party/board`: 대기 / 문제(대분류·중분류·타이머, **IMAGE 면 사진 크게**, VIDEO 면 플레이어, TEXT 면 문제, GAME 이면 열린 힌트, 재생형이면 "○팀 오답 → ○팀 기회" 표시) / 정답 공개(정답·보조·출처·득점 팀) / 점수판 / 종료 화면.
- **물리 구성**: 노트북 ↔ TV 를 HDMI 로 잇고 Windows 디스플레이를 **확장**(Win+P → "확장")으로 둔다. 복제(미러)가 아니라 확장이라 노트북 화면과 TV 가 서로 다른 바탕화면이 된다. 브라우저 창 두 개를 열어 콘솔은 노트북 화면에, 보드는 TV 쪽으로 끌어다 F11 전체화면. 마우스·키보드는 노트북에서 그대로 쓴다. **복제 모드로 두면 정답 카드가 TV 에 그대로 보이므로** 리허설 체크리스트 1번.
- **동기화**: 보드는 서버 상태를 **1초 폴링**(`GET /admin/party/board/state`, 작은 JSON)해서 그린다. 콘솔이 누른 것이 서버에 저장되고 보드가 다음 폴링에 반영(지연 최대 1초). 같은 브라우저 두 창일 필요가 없어 **휴대폰을 콘솔로 쓰는 예비 구성**도 된다.
- **예비 구성(확장 디스플레이가 안 될 때)**: "로컬"은 서버가 노트북에서 돈다는 뜻이지 노트북 브라우저만 쓸 수 있다는 뜻이 아니다. 같은 네트워크의 기기는 `http://노트북IP:8082` 로 들어온다. 핫스팟을 켠 휴대폰과 거기 붙은 노트북은 같은 LAN 이므로 휴대폰 브라우저에서 노트북 IP 로 접속(`ipconfig` 로 확인, 보통 `192.168.x.x` 또는 `172.20.10.x`). 준비: ① Windows 방화벽에서 8082 인바운드 허용 ② Spring 은 기본이 모든 인터페이스 바인딩이라 설정 변경 없음 ③ **1계정 1세션 제한** 때문에 휴대폰(콘솔)과 노트북(보드)이 같은 관리자 계정이면 서로 로그아웃시킨다 → 로컬 DB 에 관리자 계정을 하나 더 만들어 보드용으로 쓴다. 게임 상태는 세션이 아니라 서버 전체 1개라(§4-3) 계정이 달라도 같은 게임이 보인다. 이때 TV 는 노트북 복제(Win+P → 복제)로 두고 노트북엔 보드 창만 전체화면. **소리는 노트북에서 낸다**: 재생은 콘솔이 아니라 **플레이어 창**(`/admin/party/player`, 아래)이 맡으므로 휴대폰에서 [재생]을 눌러도 노트북 → HDMI → TV 로 소리가 나간다. 단, 복제 모드에선 노트북 화면이 곧 TV 라 플레이어 창의 영상이 TV 에 보인다(노래는 뮤직비디오가 정답을 드러냄) → 이 구성에서는 플레이어 창을 최소화하거나 보드 창 뒤에 둔다. 이건 YouTube 정책상 회색(가림·숨김, 기존 사이트의 O-025 와 같은 상태)이라 **확장 디스플레이가 안 될 때만** 쓴다. 리허설 1 에서 이 구성도 한 번 돌려 본다.
- **플레이어 창** `/admin/party/player`: 480×270 플레이어 하나와 현재 항목 표시만 있는 페이지. 서버 상태의 재생 명령(재생·일시정지·처음부터, 명령 순번 포함)을 1초 폴링으로 따라간다. 기본 구성에서는 **콘솔 페이지 안에 이 플레이어가 들어 있어** 별도 창이 필요 없고(콘솔 = 플레이어), 콘솔이 휴대폰일 때만 노트북에 플레이어 창을 따로 연다. 콘솔 설정에 "재생 담당: 이 창 / 플레이어 창" 토글 하나. 재생 명령이 서버를 거치므로 휴대폰에서 누르면 최대 1초 뒤 노트북이 재생한다. 플레이어 창도 첫 화면 클릭 1회 필요(자동 재생 정책). v1~v7 의 `BroadcastChannel` 안은 같은 브라우저 두 창에서만 되므로 폴링으로 교체. 보드 첫 화면 [보드 시작] 클릭 1회(브라우저 자동 재생 정책).
- **소리**: HDMI 연결 시 Windows 기본 출력이 TV 로 바뀐다(안 바뀌면 소리 설정에서 TV 선택). 출력은 시스템 전체 설정이라 어느 창의 소리든 TV 스피커로 나간다. TV 스피커가 약하면 블루투스 스피커를 기본 출력으로 — 같은 원리. 리허설 확인 항목.

### 4-2. 라운드 — 진행 패턴 3종
1. 대분류 → 중분류(노래는 5년 묶음·전체, 나머지는 DISTINCT·전체) 선택 → [랜덤 뽑기] → 서버가 이번 게임 미출제 항목 중 랜덤 1개(0 이면 선택 불가). **뒤로가기(10-06 확정)**: 대분류·중분류 선택 자체는 서버 상태를 안 바꾸므로 [랜덤 뽑기] 전엔 그냥 다른 걸 고르면 된다. 뽑힌 뒤에도 [보드에 띄우기] 전까지는 TV 가 '준비 중'이라 [다시 뽑기] 또는 [대분류 변경]으로 취소할 수 있고, **취소된 항목은 미출제로 돌아간다**(참가자가 못 봤으므로 나중에 다시 나올 수 있음). 띄운 뒤에는 취소 없이 [못 맞힘]으로 넘긴다.
2. 제시 방식이 패턴을 정한다:

| 패턴 | 대분류 | 흐름 |
|---|---|---|
| **A 정지형** (IMAGE·TEXT) | PERSON · SCREEN · ANIME 장면 · QUIZ | 보드에 사진/문제 → 외침 → MC [팀 정답] → 정답 공개 → [다음]. 오답이면 상대 팀 기회, 둘 다 못 맞히면 [못 맞힘]. 힌트 없음, **타이머 없음**(10-06) |
| **B 재생형** (AUDIO) | SONG · ANIME OP/ED · SOUND · GAME 게임 맞히기 | 콘솔 재생 → "정답!" 외침에 MC [일시정지] → 맞으면 [팀 정답] → 끝. 틀리면 [○팀 오답] + [재생] 재개, 상대 팀 기회 → 외침에 [일시정지] → 맞으면 끝, 틀리면 **끝까지 재생하며 자유 도전**(10-06: 1절까지는 팀당 1회씩, 그 뒤는 양 팀 무제한 — 먼저 맞히는 팀 득점, 경계는 MC 판단. 앱은 [○팀 오답] 2회 뒤에도 [팀 정답] 버튼을 잠그지 않고 보드에 "자유 도전" 표시) → 끝까지 안 나오면 [못 맞힘] |
| **C 재생형 + 힌트** (AUDIO) | GAME 캐릭터 맞히기 | B 와 같되(자유 도전 포함) 클립이 짧아 아무도 못 맞히면 MC 가 [힌트 열기] 1 → 2 → 3 을 보드에 띄우고 [처음부터] 재생을 반복. 다 열고도 못 맞히면 [못 맞힘] |

3. [팀 정답] → 점수 1(=탈출 1명) → 보드 정답 공개(정답·보조·출처) → [다음 라운드]. 점수 ± 로 정정.
4. [○팀 오답] 은 점수와 무관한 **보드 표시**(그 팀 배지 흐리게 + "○팀 기회")라 참가자도 상황을 안다. 안 눌러도 진행엔 지장 없고 규칙 강제는 MC.
5. 다음 대분류는 MC 재량(§6). 라운드 수 제한 없음. 탈출으로 판이 끝나면 [종료] 또는 계속(무한). 종료 시 결과 화면 + JSON.

### 4-3. 상태·복구
**게임 상태는 로그인 세션이 아니라 서버 전체에 1개**(`PartyGameHolder` 싱글턴 빈이 `PartyGameState` 를 들고 있음. 스피드퀴즈도 같은 방식). 파티는 한 번에 한 판이므로 "현재 게임"은 하나뿐이고, 어느 관리자 계정·어느 기기로 들어와도 같은 게임을 본다 — 콘솔과 보드가 다른 계정·다른 기기여도 된다(§4-1 예비 구성의 전제). v1~v7 의 `HttpSession` 안은 같은 브라우저 두 창에서만 우연히 되는 구조라 폐기.
- 복구: 상태가 바뀔 때마다 JSON 스냅샷을 노트북 파일(`party-state.json`, 업로드 폴더 옆)에 쓰고, 기동 시 있으면 읽어 복원한다. 콘솔·보드 새로고침은 물론 **앱 재시작·노트북 재부팅 뒤에도 이어서 진행**. DB 저장 없음.
- **출제 이력과 연습경기(10-06)**: 상태는 두 층이다. ① 이번 판(라운드·점수·현재 항목) ② **누적 출제 이력**(참가자에게 띄운 `party_item` id·`song` id 집합 — 취소된 항목은 제외). [새 게임]은 두 가지: **[새 게임 · 이력 유지]** = ①만 초기화, ②는 남김 → 연습경기에서 보여준 문제는 본게임에 안 나온다 / **[전부 초기화]** = ①② 모두 삭제(리허설 뒤 행사 당일 시작 전에 한 번). 연습경기는 별도 화면이 아니라 그냥 한 판을 하고 [새 게임 · 이력 유지]로 본게임을 시작하는 것. 콘솔 헤더에 "이번 판 n · 누적 m · 남은 x"를 보여 주고, 남은 개수는 누적 이력을 뺀 값이다. 스피드퀴즈는 별도(설정 저장 때 제시어 이력 초기화, 그대로).
- 동시성: 콘솔은 하나뿐이라 락은 필요 없고, 홀더 갱신은 `synchronized` 한 줄이면 충분하다. 보드는 읽기만 한다.

### 4-4. 하지 않을 것

## 10. 로컬 인스턴스 결정 근거 (2026-09-29 질문 → **로컬 확정**, 반영은 §0·§1·§2-3·§3·§5·§7)

**코드는 같다.** 달라지는 건 ① 저작권 여지 ② 운영 방식 ③ 당일 위험 셋이다.

### 10-1. 저작권 — 사진·캡처가 "불가"에서 "회색·저위험"으로 내려온다
- 운영 서버: 사진·캡처 파일을 올리는 순간 **복제 + 공중송신**. 관리자 전용 경로라도 서버에 있으면 같다 → 불가.
- 로컬(노트북 안에만 두고 현장 상영): 복제는 제30조 **사적 이용을 위한 복제**(비영리 · 개인적 이용 또는 "가정 및 이에 준하는 한정된 범위") 안에 들 여지가 있고, 상영은 제29조, 전송은 없다. "가정에 준하는 한정된 범위"는 구성원 사이에 강한 개인적 결합이 있는 소수 집단으로 해석되고 인원 기준선은 없다 — 고등학교 친구·연인 15명은 대체로 해당한다고 보지만 확정된 선은 아니다(회색, 위험 낮음).
- 조건: 캡처 원본은 정당하게 접근한 화면(OTT 구독·방송·공식 유튜브)에서. 불법 복제물에서 뜬 캡처는 제30조 논의에서 빠진다. 파일은 **git·서버에 절대 올리지 않는다**(노트북 폴더만, `.gitignore`).
- 인물 사진: 사진저작권(촬영자·소속사)은 위와 같은 사적 복제 여지. 초상권·퍼블리시티권은 영리 이용이 아니고 사적 모임 안 표시라 문제 삼기 어렵다.
- YouTube 는 로컬이어도 같다: 임베드는 보이게, **다운로드는 약관 위반**(저작권 쪽은 제30조 여지가 있어도 계약 위반은 남는다). 오프라인 대비 파일 다운로드는 권하지 않는다. 기존 코드에 MP3 `file_path` 재생 경로가 데드 코드로 남아 있지만(O-005) 되살리지 않는다.
