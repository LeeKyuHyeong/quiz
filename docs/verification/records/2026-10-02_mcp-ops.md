## 1. 요청과 목적
- 사용자가 원한 것: 티빙 AI Ops 지원 전, quiz 의 운영 기능을 Java MCP 서버 도구로 노출해 Claude Code 에서 호출해 본다. 계획·범위·AC 는 career `20-applications/2026-10-tving/jd-map.md` §11(10-02 아침 본인 결정).
- 개발자 확인 결과(결정 사항, §11): `main`(2bc7fea) 에서 `feat/mcp-ops` · 전송은 앱 안 SSE(`/sse` + POST `/mcp/message`) · prod 는 비활성 · 읽기 3개(곡 신고 목록·배치 상태·회원 검색)는 기존 서비스 재사용·새 쿼리 없음 · 쓰기 1개(신고 처리)는 `confirm=true` 뒤에만 실행 + 호출 감사 로그 테이블 · 회원 정지는 범위 밖.
- 진행 중 둔 가정(본인 확인 요청):
  1. **쓰기 도구의 처리자 계정** — SSE 전송에는 로그인 주체가 없다. `quiz.mcp.admin-email`(환경변수 `QUIZ_MCP_ADMIN_EMAIL`) 로 지정한 회원이 `role=ADMIN` 일 때만 `SongReportService.processReport` 를 그 계정으로 부른다. dev 기본값은 `a@a.com`(DataInitializer 관리자). 감사 로그의 호출 주체 식별값도 이 이메일.
  2. **감사 로그는 읽기 도구 호출도 남긴다**(§11 은 쓰기 도구 줄에 적혀 있었음) — 운영 조회 흔적도 남기는 편이 티빙 J5(감사) 설명에 맞다고 봄. 비용은 호출당 INSERT 1건.
  3. **기본값은 꺼짐**(`application.properties` `spring.ai.mcp.server.enabled=false`), dev 프로파일만 켠다. §11 의 "prod 프로파일은 false" 보다 한 단계 보수적(test·session-* 등 다른 조합에서도 꺼짐).
  4. 전송은 §11 대로 SSE(Spring AI 1.1 기본). MCP 스펙의 최신 전송은 Streamable HTTP(`spring.ai.mcp.server.protocol=STREAMABLE`)이지만 Claude Code 는 둘 다 붙으므로 계획을 바꾸지 않았다.
  5. 정확한 버전은 **Spring AI 1.1.8**(Maven Central `maven-metadata.xml` 의 1.1.x 마지막, BOM·`spring-ai-starter-mcp-server-webmvc` 모두 존재 확인). 끌려오는 MCP Java SDK 0.18.3.

## 4. 영향 범위 분석
- 검색한 호출처와 결과: `processReport`·`getReports` 호출처는 `AdminSongReportController` 뿐(변경 없음). `SecurityConfig` CSRF 예외는 기존 2개에 1개 추가, `authorizeHttpRequests` 순서는 손대지 않음(`/sse`·`/mcp/message` 는 `anyRequest().permitAll()` 에 해당 — dev 전용이라 허용, 운영은 404).
- 영향 받는 화면/기능: 없음. 서버가 꺼진 기본값에서는 `McpToolsConfig` 빈도 생기지 않는다. 다른 `@SpringBootTest` 컨텍스트는 `enabled=false`(test 리소스에 별도 설정 없음 → 기본값) 라 MCP 자동구성 자체가 안 뜬다.
- 스타터가 끌어오는 의존성: `spring-ai-model`·`spring-ai-mcp`·MCP SDK 0.18.3·`mcp-spring-webmvc`. 기존 Jackson/Reactor 와 충돌 없음(빌드·회귀로 확인).
- 켜진 상태의 부작용 1건: 열린 SSE 연결은 Tomcat 활성 요청으로 잡혀 **graceful shutdown(Boot 3.4 기본, `timeout-per-shutdown-phase` 30초)** 이 그만큼 기다린다. 테스트 컨텍스트는 2초로 단축. 운영은 꺼져 있어 해당 없음, dev 재시작이 느리면 이 때문.

## 8. 발견된 문제와 조치
- **`/mcp/message` 403** — Spring Security CSRF 가 MCP 의 JSON-RPC POST 를 막음. 조치: CSRF 예외 1줄(§3). 테스트: `McpServerToolsTest$Enabled` 3건이 이 상태에서 실패했다가 통과.
- **테스트 JVM 종료 30초 지연**(`Surefire is going to kill self fork JVM`) — jstack: `tomcat-shutdown` 이 `GracefulShutdown.awaitInactiveOrAborted` 에서 대기, 열린 SSE 응답이 활성 요청. 조치: 해당 테스트 컨텍스트만 `spring.lifecycle.timeout-per-shutdown-phase=2s`. 운영 코드 변경 없음(§4 부작용 기록).
- **날짜가 `[2026,9,21,22,35,53,…]` 배열로 직렬화** — MCP 서버 결과 변환기의 기본 ObjectMapper. 조치: 응답 record 의 날짜를 ISO 문자열로. 테스트 `datesAreIsoStrings`(실패 확인 뒤 통과).
- (환경) Docker Desktop 이 stale 소켓(`run\dockerInference`)으로 기동 실패 → 메모리에 적힌 디렉터리 이름 바꾸기 절차로 복구, 29.4.2 확인. 코드 무관.

## 9. 미검증 영역과 남은 위험
- **운영 DB 테이블 미생성(O-031)** — main 머지·push 전에 운영 `song` DB 에 `schema.sql` 의 `mcp_tool_audit_log` CREATE 를 실행해야 한다. 안 하면 새 색 기동 실패로 배포가 멈춘다(전환은 안 되므로 서비스 영향은 없음).
- **운영 노출** — 운영은 `enabled=false` 기본값이라 `/sse` 404(AC-9 는 test 프로파일 + 속성으로 확인, 실제 prod 컨테이너는 배포 뒤 Smoke 로 `curl -A "Mozilla/5.0" https://game.kyuhyeong.com/sse` → 404 확인 🙋). 켤 경우 `/sse`·`/mcp/message` 는 인증 없이 열리고 CSRF 예외도 함께 열린다 — 운영에서 켜려면 인증(토큰·IP 제한)이 먼저다.
- **LLM 쪽 confirm 흐름** — "confirm=true 는 사용자 확인 뒤에만" 은 도구 설명(description)으로만 유도한다. 모델이 바로 `confirm=true` 로 부르는 것을 서버가 막지는 못한다(설계상 사용자-모델 사이 합의). 더 막으려면 dry-run 응답에 1회용 토큰을 실어 실행 호출이 그 토큰을 돌려주게 해야 한다 — 범위 밖.
- **감사 로그 보존** — 정리 배치 없음. 호출당 1행이라 당분간 문제없음.
- H2 `MODE=MariaDB` 라 `bit(1)`·`datetime(6)` 매핑은 로컬 MariaDB `validate` 기동으로만 확인(✅).
